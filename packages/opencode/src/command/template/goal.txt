Drive the orchestrator loop until the active goal is achieved.

An active goal has already been persisted for this session by the `/goal <condition>` dispatcher. The persisted fields are visible via `goal(action="status")`:

- `condition` — the user's stated outcome (verbatim)
- `planPath` — where to read/write plan.md (defaults to `./plan.md`)
- `priority` — `low` | `normal` | `high`
- `iterationCount` — number of reviewer verdicts recorded so far

Your responsibility while a goal is active:

1. **Confirm the goal state first.** Call `goal(action="status")` to read the active goal's condition and current iteration. Do not re-issue `goal(action="set")` — the user already supplied the condition.

2. **Read or generate `plan.md`.** If a plan file already exists at `planPath`, read it. Otherwise create `<worktree>/plan.md` with three sections:

   - **Goal** — the condition, verbatim
   - **Steps** — numbered list of sub-tasks to satisfy the goal
   - **Exit criteria** — a testable, mechanical check the reviewer will judge against (e.g. "all packages pass `bun typecheck`", "`grep -r 'TODO' src/` returns no hits", "the new endpoint returns 200 on `curl localhost:3000/healthz`")

3. **Spawn coder subagents** (`task` tool, agent=`coder`) to execute steps in parallel where safe. Do not edit code yourself — keep your context clean for orchestration.

4. **After each round of coder work, dispatch the reviewer** with:

   - `paths: [plan.md, ...changed files]`
   - `description`: "judge whether the changes in this iteration satisfy plan.md's exit criteria"
   - `reason`: "goal iteration {N}"

5. **On reviewer verdict**:

   - `pass` → call `goal(action="complete")`, surface a one-paragraph summary to the user, the loop ends.
   - `fail` or `blocked` → update plan.md (mark failed steps, add new steps if needed), call `goal(action="record_review", reviewID=<reviewID>, verdict=<verdict>, reason=<text>)` to bump `iterationCount`, loop back to step 3.
   - If the same verdict returns 3 times in a row, surface to the user — the plan may be infeasible.

6. **Hard constraints during /goal**:
   - Never edit code yourself — only orchestrate via `task`, `subagent_message`, `mesh_control`, `goal` (read/write), and `write`/`read`.
   - Never call `goal(action="block")` until you've exhausted `banyancode_max_goal_iterations` retries. Use `fail` verdicts to iterate.
   - If the plan is clearly infeasible (user asked for the impossible), call `goal(action="block", reason=<text>)` and let the user decide.

Sub-commands (handled by the `/goal` dispatcher before this template runs — do NOT call them yourself):

- `/goal <condition> [--plan <path>] [--priority low|normal|high]` — persists a new active goal, then runs this template
- `/goal status` — print the active goal (no agent invocation)
- `/goal cancel` — cancel the active goal (no agent invocation)
- bare `/goal` — print the active goal if one exists, otherwise show usage (no agent invocation)

This loop replaces any "stop after N steps" behavior. Do not manually count steps. The loop is bounded by goal achievement, not by a step count.
