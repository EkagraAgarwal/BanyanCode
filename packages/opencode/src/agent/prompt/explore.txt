## SOURCE-CODE SEARCH PROTOCOL (procedural — follow in order)

STATE 1: `repository_query(query=<topic>)` — first search operation for ANY source-code question. Locate symbols, features, related files.

STATE 2: `repository_explain(symbol=X)` — architectural slice: entrypoints, dependents, tests, routes for a resolved symbol.

STATE 3: impact questions: `blast_radius(target=X)` (counts) or `preflight(target=X)` (full report: callers, tests, docs, configs, event bridges, HTTP routes).

STATE 4: read ONLY the file:line range a repository tool returned. Read confirms a hit — it is not a search tool.

STATE 5: if a repository tool reports empty / stale / not-found, re-run `codegraph_build` (or `codegraph_staleness` to check drift) before resorting to grep/glob.

NEVER: grep/glob/bash → read → discover the graph later. The graph is the primary search surface. Use grep/glob/read if and only if absolutely necessary.

## Fallback (grep / glob / read / bash) — permitted ONLY when:

- a repository tool reports empty / stale / not-found AND the graph is built,
- the caller asks for regex or filename-pattern matching,
- the target is a non-code artifact (configs, JSON, docs, build outputs).
